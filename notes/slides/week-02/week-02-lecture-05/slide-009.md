# Slide 9

![Original slide 9](../../../public/generated/week-02-lecture-05/slide-009.png)

## Explanation

This slide traces one TCP data unit across a path with a router. Each layer creates or checks protection for its own protocol data unit (PDU). The application creates data, TCP adds a checksum, IP adds its checksum, and Ethernet adds an FCS around the IP datagram for each local link. [week-02-lecture-05, p. 9]

## Walkthrough

At the sender:

1. The application produces an application PDU.
2. TCP encapsulates it and generates the TCP checksum (**GTC**).
3. IP encapsulates the TCP PDU and generates the IP checksum (**GIC**).
4. Ethernet encapsulates the IP datagram and generates the Ethernet FCS (**GEF**).

At the router, the incoming Ethernet frame is checked (**CEF**) and removed. The router checks the IP checksum (**CIC**), makes its routing decision, and then sends the same IP datagram in a new Ethernet frame on the next interface. That new frame gets a new Ethernet header and a newly generated FCS. At the destination, the checks happen in the reverse direction: Ethernet FCS, IP checksum, and TCP checksum are checked before the data reaches the application. [week-02-lecture-05, p. 9]

## Connections and exam relevance

The diagram reinforces the important scope distinction: Ethernet protection is regenerated at every hop, but the TCP checksum is generated by the original sender and checked by the final receiver. A router does not normally recalculate the TCP checksum because it forwards the IP packet without interpreting the TCP payload. [week-02-lecture-05, p. 9]

## Check your understanding

At the router, why is a new Ethernet FCS generated even though the IP datagram is being forwarded?

Student response: The Ethernet frame is local to each link, so the router creates a new frame and a new FCS for the next hop.

## Week 2 Exam Review Summary

This is the condensed review for all five Week 2 lectures. Use it as the first place to revise; return to the individual slides only when you need a fuller explanation or diagram.

### 1. Facts and distinctions to memorize

#### Socket types and protocols

- `socket(AF_INET, SOCK_STREAM, 0)` means IPv4 + reliable byte-stream abstraction + default protocol: **TCP**.
- `socket(AF_INET, SOCK_DGRAM, 0)` means IPv4 + independent datagrams: **UDP**.
- `SOCK_RAW` exposes lower-level IP packets rather than TCP/UDP’s normal transport abstraction. **ICMP is its own IP-layer protocol**, not TCP or UDP; raw does not mean “unknown protocol.”
- A **stream** is an ordered flow of bytes with no preserved message boundaries. A **datagram** is one self-contained message unit whose boundary is preserved by the datagram API. `[week-02-lecture-01, pp. 5, 24]`

#### TCP server/client lifecycle

Memorize the normal call sequences:

```text
TCP server: socket → bind → listen → accept → read/write → close
TCP client: socket → connect → write/read → close
```

- `socket()` creates an operating-system socket descriptor.
- `bind()` assigns a local IP address and port. A server normally binds a known port so clients know where to find the service. A client can usually receive an automatically chosen ephemeral port.
- `listen()` turns a bound TCP socket into a passive listening socket and establishes a backlog queue. It does not exchange application data and does not itself create the connected socket.
- `accept()` removes one pending connection from the queue and returns a **new connected descriptor**. The original descriptor remains the listening descriptor.
- `connect()` is the client-side request that causes TCP connection establishment through the three-way handshake: `SYN → SYN/ACK → ACK`.
- After `accept()`, use the returned connected descriptor for that client’s data. Keep the listening descriptor open for future clients.
- `close()` releases the descriptor. A server normally closes the connected descriptor for a finished client but keeps the listening descriptor open. `[week-02-lecture-01, pp. 2–12]`

#### TCP stream behavior

- TCP preserves byte order and reliability, but it does **not** preserve application message boundaries.
- One `write()` is not guaranteed to match one `read()`.
- A `read()` may return fewer bytes than requested. If the application expects 100 bytes and receives 40, it must continue reading until it has the remaining 60, reaches its framing rule, sees EOF (`read()` returns `0`), or encounters an error.
- Applications need a framing rule for logical messages: fixed length, delimiter, or length prefix. `[week-02-lecture-01, pp. 10, 23]`

#### Concurrent TCP servers

- **Iterative server:** accepts one client, finishes that client, closes its connected descriptor, then accepts the next. It is simple and adequate for short transactions, but a slow client delays everyone behind it.
- **Concurrent server:** accepts a client and uses `fork()` to create a child process for that client.
- After `fork()`:
  - child receives return value `0`, closes the listening descriptor, handles `new_sd`, and exits after the client is done;
  - parent receives a positive child PID, closes its copy of `new_sd`, and immediately returns to `accept()`;
  - `-1` means `fork()` failed.
- `accept()` creates the connected socket; `fork()` creates the child process. They are different operations.
- Multiple connections can share one server port because TCP identifies each connection by the four-tuple:

```text
(source IP, source port, destination IP, destination port)
```

The server’s destination port can be the same for every client; different client IP/port values distinguish the connections. `[week-02-lecture-01, pp. 13–22]`

#### UDP lifecycle and API

Memorize the contrast:

```text
UDP server: socket → bind → recvfrom → sendto → ...
UDP client: socket → sendto → recvfrom → close
```

- UDP does not require `listen()` or `accept()` because it has no TCP-style connection handshake.
- The UDP server binds a known local port and can receive datagrams from many clients through one socket.
- `recvfrom()` receives one datagram and populates the sender’s address structure.
- `sendto()` uses that address structure to send the reply to the correct client.
- UDP preserves datagram boundaries but does not provide TCP’s built-in reliability, ordering, flow control, or retransmission.
- UDP still uses `close()` because the socket is an operating-system resource, even though there is no connection to terminate.
- Calling `connect()` on a UDP socket only records a default peer. It does not perform a handshake and does not make UDP reliable. It allows the client to use `read()`/`write()` instead of repeatedly supplying the server address; the underlying packets remain UDP datagrams. `[week-02-lecture-01, pp. 24–37]`

#### Important socket/address details

- `AF_INET` means IPv4.
- `INADDR_ANY` means bind to any local interface.
- `htons()`/`htonl()` convert host-order values to network byte order before placing them in network address structures.
- `0` as a requested port lets the operating system choose an available ephemeral port. `[week-02-lecture-01, pp. 5–8, 35]`

### 2. Layer models and responsibilities

#### OSI model

The OSI model is a **conceptual reference framework**, not a claim that every network contains seven separate physical components. Data moves down the sender’s stack, crosses the network, and moves up the receiver’s stack; same-layer horizontal arrows represent a logical peer relationship. `[week-02-lecture-02, pp. 1–2]`

| OSI layer | Main exam idea |
| --- | --- |
| Application | User-facing network services and application protocols such as HTTP, FTP, SSH, email, and VoIP. |
| Presentation | Data representation/translation, encoding, encryption, and compression. |
| Session | Establishing, managing, and ending a logical conversation/session. |
| Transport | End-to-end delivery between processes; TCP/UDP, ports, flow/error control, and connection behavior. |
| Network | IP logical addressing and routing across multiple networks. |
| Data link | Local one-hop framing, MAC addressing, media access, and link-level error/flow control. |
| Physical | Bits represented as electrical, optical, or radio signals over a medium. |

The practical TCP/IP grouping is:

```text
OSI Application + Presentation + Session → TCP/IP Application
OSI Transport → TCP/IP Transport
OSI Network → TCP/IP Internet/IP
OSI Data Link + Physical → TCP/IP Link
```

Do not confuse the OSI layer names with the exact implementation of the Internet. `[week-02-lecture-02, pp. 1–10, 34]`

#### PDU names and encapsulation

As data moves downward, each layer adds its own control information. The standard vocabulary is:

```text
Application data/message
    ↓ transport header
TCP segment or UDP datagram
    ↓ IP header
IP packet/datagram
    ↓ link header + trailer
Link-layer frame
    ↓ signal representation
Physical bits/signals
```

At the receiver, decapsulation removes the appropriate header/trailer as the data moves upward. The physical layer transmits signal representations rather than interpreting application headers. `[week-02-lecture-02, p. 10; week-02-lecture-04, p. 1]`

#### The Internet hourglass and changing link technologies

- IP is the Internet’s narrow waist: many applications and transport protocols can operate above it, and many link/physical technologies can carry it below.
- An IP packet can travel over Ethernet on one hop, Wi‑Fi on another, and PPP, SONET, or another technology elsewhere.
- At a router, the old link-layer frame is removed and the same IP packet is placed into a new frame appropriate for the next link.
- Higher-level protocols such as HTTP do not need to know whether the current lower link is Ethernet or SONET, as long as the IP service contract is met. `[week-02-lecture-02, pp. 12–15]`

#### Device and address roles

- A **host** participates in the higher layers and is an endpoint for transport/application communication.
- A **switch** is primarily a Layer 2 device. It forwards local frames using a destination MAC address and a MAC-address-to-port table.
- A **router/Layer 3 switch** forwards packets between IP networks using IP information and routing decisions.
- A **hub/repeater** works at the physical level by repeating or regenerating signals; it does not route using IP.
- A **MAC address** identifies a local-link network interface. A standard MAC is 48 bits, normally written as 12 hexadecimal digits. A device normally has one MAC per relevant interface.
- An **IP address** is normally assigned per interface and provides both endpoint identification and logical network location. A laptop with Ethernet and Wi‑Fi normally has separate MAC and IP addresses for the two interfaces. `[week-02-lecture-02, pp. 16–20, 26]`

#### Switch versus router: the exam trace

- Switch: consult destination MAC → select local output port → forward the current frame.
- Router: inspect the IP destination → consult routing information → choose an outgoing interface/next hop → remove the incoming frame → create a new outgoing frame.
- Across a router, the **MAC addresses change** because the frame is local to each hop.
- The source and destination **IP addresses remain the end-to-end addresses** in the course’s forwarding example.
- The router does not mathematically derive a MAC from an IP. It chooses the next hop using routing information, then a local mechanism such as ARP for IPv4 or Neighbor Discovery for IPv6 resolves the next-hop IP to a MAC. The switch then forwards the frame using that MAC. `[week-02-lecture-02, pp. 11, 24–28]`

#### Local versus end-to-end control

- Data-link error/flow control covers one link between neighboring nodes.
- Transport error/flow control covers the complete path between the two end systems.
- Both can exist at the same time: a link may repair a local loss, while TCP still protects the complete end-to-end transfer.
- A successful hop does not prove that the packet reached the destination; a later link can still lose it, so transport-level end-to-end control remains necessary. `[week-02-lecture-02, pp. 29–30]`

#### Segmentation, fragmentation, and MTU

- **Transport segmentation:** the source transport layer divides application data into multiple TCP segments or other transport units; the destination transport layer collects, orders, and reconstructs them.
- **IP fragmentation:** an IP packet is split when it exceeds a smaller link’s MTU (maximum transmission unit). In the course’s IPv4 example, the destination reassembles the fragments; intermediate routers normally forward them rather than reconstructing the original packet.
- Frames are local and may be replaced at every router. IP fragments remain part of the end-to-end network-layer transfer. `[week-02-lecture-02, pp. 31–33]`

### 3. Physical-layer formulas and concepts

Memorize the distinctions before memorizing the formulas:

- **Bandwidth:** maximum capacity of a link.
- **Bit rate:** actual bits sent per second.
- **Error rate:** fraction/percentage of received bits that are incorrect.
- **Latency:** elapsed time for the message to reach the other side.
- High bandwidth does not automatically mean low latency.

#### Core formulas

Transmission delay—the time to put all $M$ bits onto a link of rate $R$:

$$
d_{trans} = \frac{M}{R}
$$

Propagation delay—the time for the signal to travel a distance $L$ at speed $v$:

$$
d_{prop} = \frac{L}{v}
$$

The simplified single-link message latency used in the lecture is:

$$
d_{message} = \frac{M}{R} + \frac{L}{v}
$$

In a real network, processing and queueing delays may also contribute. Increasing $R$ reduces transmission delay, but it does not necessarily reduce propagation delay; propagation mainly depends on distance and signal speed. `[week-02-lecture-03, pp. 1–6]`

#### Calculation habits

- Convert bytes to bits before using a bit/s rate: `bytes × 8 = bits`.
- Convert `kbps` to `1000 bits/s` and `ms` to seconds or vice versa before adding.
- For two equal store-and-forward links of length $x$, propagation speed $y$, message size $L$ bits, and rate $R$:

```text
total propagation = 2x/y
total transmission = 2L/R
total delay = 2x/y + 2L/R
```

If the two parts are set equal, `$2x/y = 2L/R$`, then `$x = Ly/R$`. The factor of two appears because the message crosses two links. `[week-02-lecture-03, pp. 6–7]`

### 4. Data-link layer and error control

#### Link-layer responsibilities

- Encapsulate an IP packet in a local frame with a link header and trailer.
- Deliver the frame across one local link.
- Use MAC addressing and media-access rules on shared media.
- Detect local corruption and, when supported, discard or retransmit a damaged frame.
- Common link technologies include Ethernet, IEEE 802.11 Wi‑Fi, PPP, and HDLC. The link protocol can change from hop to hop while IP remains the common network-layer service. `[week-02-lecture-04, pp. 1–3]`

Do not confuse:

- **MAC address:** a link-layer identifier for an interface.
- **Media Access Control:** the link-layer rules for deciding who may transmit on a shared medium.

#### Error patterns

- **Single-bit error:** one bit changes.
- **Multiple-bit error:** two or more bits change, not necessarily adjacent.
- **Burst error:** two or more consecutive bits change. `[week-02-lecture-05, p. 2]`

#### FCS/CRC and checksum logic

The sender computes an error-detection value and appends it to the data. The receiver recomputes the value from what it received and compares the results.

For an FCS:

```text
sender:   [H | D | f(D)]
receiver: receive D' and f(D), calculate f(D')
error if: f(D') ≠ f(D)
```

- **FCS (Frame Check Sequence):** error-detection field in a link-layer frame, normally in the trailer.
- **CRC (Cyclic Redundancy Check):** a strong error-detection method commonly used to produce an FCS; it is based on polynomial division rather than a simple additive checksum.
- A checksum is generally simpler and cheaper but weaker. CRC is more computationally involved and generally stronger for common transmission-error patterns.
- Ethernet, 802.11, and DSL are examples of link technologies using CRC-style checks.
- Detection is not the same as correction. The FCS/CRC says the frame failed a check; a separate protocol action such as retransmission performs recovery. `[week-02-lecture-05, pp. 3–7]`

#### Checksum scope

- The course slide states that the IP checksum is computed only over the IP header, so it cannot detect an error occurring only in the IP payload.
- The TCP checksum covers the TCP header and payload in the course’s comparison.
- Therefore, a packet can have multiple checks at different layers, each protecting a different scope. A lower-layer check can reject a damaged frame while an end-to-end transport check still protects delivery across the full path. `[week-02-lecture-05, pp. 5–9]`

#### Layered error-handling trace

1. Sender generates the TCP checksum.
2. Sender generates the IP checksum.
3. Sender generates the local Ethernet FCS.
4. Each receiver/router checks the local Ethernet FCS. A bad frame is rejected; on a technology such as 802.11, local retransmission may occur.
5. A router removes the old Ethernet wrapper, checks/uses the IP packet, and creates a new Ethernet frame with a new local FCS for the next hop.
6. The final host checks Ethernet, IP, and TCP information before delivering data upward.
7. If local recovery fails, TCP may observe missing or delayed data and retransmit end-to-end. UDP does not automatically provide that TCP-style recovery. `[week-02-lecture-05, pp. 8–9]`

### 5. Common exam traps

1. **`listen()` is not `accept()`:** `listen()` prepares a passive socket and queue; `accept()` returns a new connected descriptor.
2. **Do not close the wrong TCP descriptor:** the parent keeps the listening descriptor; the child keeps the connected descriptor.
3. **TCP is a byte stream:** never assume one `write()` equals one `read()`.
4. **UDP `connect()` is not a handshake:** it stores a default peer; it does not add TCP reliability.
5. **UDP still needs `close()`:** close releases the OS resource even without a transport connection.
6. **MAC and IP have different scopes:** MAC is local-hop/interface addressing; IP is network-layer routing/end-to-end addressing.
7. **Switch versus router:** switches use destination MAC and ports; routers use IP and routing information.
8. **Frames versus packets:** frames are replaced at routers; the IP packet is carried inside a new frame on each link.
9. **Transmission versus propagation delay:** `$M/R$` is putting bits onto the medium; `$L/v$` is signal travel through the medium.
10. **Checksum/FCS detects; retransmission recovers:** do not claim that a checksum or CRC automatically repairs corrupted data.
11. **IP fragmentation is not transport segmentation:** fragmentation adapts an IP packet to MTU; transport segmentation divides application data for the transport layer.
12. **A passing check is not an absolute proof:** it means the chosen detection function found no mismatch for the protected fields.

### One-sentence mental model

**Applications create data; TCP or UDP provides an end-to-end transport service; IP routes packets across networks; each link wraps the packet in a hop-specific frame; the physical layer sends the bits; local checks protect each hop while transport checks and recovery protect the complete communication.**
